Daily Learnings: DynamoDB Single-Table Design Patterns

Mar 15, 2026 DynamoDB Learning

This week I went deep on DynamoDB single-table design. It's one of those topics where the more you learn, the more you realize the mental model is fundamentally different from relational databases. Here are my notes and key takeaways.

The Core Mental Shift

In relational databases, you model your data first and figure out queries later. With DynamoDB, it's the opposite: start with your access patterns, then design your table structure to serve them.

This feels backwards at first, but it makes sense when you consider that DynamoDB is optimized for known access patterns at any scale. You're essentially pre-computing your query results in how you structure your data.

Access Pattern Worksheet

Before touching any code, I now create an access pattern worksheet for every new DynamoDB table. It looks like this: 

# Access Patterns for User Service

1. Get user by ID              → PK: USER#userId, SK: PROFILE
2. Get user's projects         → PK: USER#userId, SK: begins_with(PROJECT#)
3. Get project by ID           → PK: PROJECT#projectId, SK: META
4. List project members        → PK: PROJECT#projectId, SK: begins_with(MEMBER#)
5. Get user by email (login)   → GSI1: email, GSI1SK: USER
6. List recent projects        → GSI2: status, GSI2SK: createdAt

This worksheet becomes the single source of truth for the table design. Every key structure and GSI exists to serve a specific, documented access pattern.

Composite Keys Are Everything

The power of single-table design comes from composite sort keys. By using prefixes like PROJECT#, MEMBER#, and INVOICE# in your sort key, you can store multiple entity types in one table and query them efficiently using begins_with.

The partition key groups related items together, and the sort key lets you efficiently query within that group. It's elegant once it clicks, but it requires discipline to maintain the key design conventions.

When Single-Table Doesn't Make Sense

Not everything belongs in one table. I've found that single-table design works best when:

  • Your entities are genuinely related and frequently queried together
  • You have well-defined, stable access patterns
  • You need the performance benefits of co-locating related data

For truly independent services with no shared access patterns, separate tables are simpler to reason about, deploy independently, and manage capacity for.

GSI Overloading

One of the more advanced patterns is GSI overloading — using the same Global Secondary Index for multiple entity types by using generic attribute names like GSI1PK and GSI1SK. This lets you keep your GSI count low (DynamoDB limits you to 20 per table) while supporting many different query patterns.

The tradeoff is readability. Your table structure becomes harder to understand at a glance. Good documentation and naming conventions become essential.

Tools That Helped

A few resources that accelerated my understanding:

  • Alex DeBrie's "The DynamoDB Book" — the definitive resource. Worth every penny.
  • NoSQL Workbench — AWS's free visual tool for modeling DynamoDB tables. Great for validating your key design before writing code.
  • Jeremy Daly's DynamoDB talks — excellent conference talks that walk through real-world design scenarios.

Key Takeaway

DynamoDB rewards you for knowing your access patterns upfront. If you design your keys around how you'll query, everything else falls into place. If you don't, you'll fight the database at every turn.
