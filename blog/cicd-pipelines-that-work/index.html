CI/CD Pipelines That Actually Work

By Pardeep Dhingra
$ gh run list --workflow=deploy.yml --limit=10
STATUS DURATION BRANCH ✗ failure 47m 22s main deploy: bump version ✗ failure 43m 11s main fix: retry deploy ✗ failure 51m 04s main fix: actually fix deploy ✓ success 44m 58s main Merge PR #211 ✓ success 46m 12s main Merge PR #208

That's a real pipeline history. Three failed deploys in a row, each taking 45+ minutes to tell you it failed. That's two and a half hours of developer time, wasted on feedback that could have arrived in four minutes.

Most CI/CD pipelines aren't bad because the tools are bad. GitHub Actions, CircleCI, and GitLab CI are all fine. They're bad because of structural decisions made early that compound over time: running everything serially, not caching, testing at the wrong layer, deploying the wrong artifact. This post is about the structural patterns that fix those problems.

The Core Problem: Sequential Everything

The default GitHub Actions workflow runs jobs one after another. Install dependencies. Lint. Test. Build. Deploy. Each step waits for the last. A 40-minute pipeline is almost always a sequential pipeline. Parallelism is the first thing to fix.

But parallelism alone isn't the answer. The second problem is running the wrong tests at the wrong time. Integration tests that spin up Docker, seed a database, and hit real endpoints take 8–15 minutes. Running those on every push to a feature branch is expensive and slow. Unit tests that run in-process take 30 seconds. You want those on every commit. The architecture of your pipeline should match the architecture of your test suite.

Test Layers and When to Run Them

This is the most important structural decision you'll make. Three layers, three triggers:

Layer 1 — Unit tests: in-process, no network, no database. Target: under 60 seconds. Run on every push to every branch.

Layer 2 — Integration tests: real database (Dockerised), real queues, fake HTTP. Target: under 5 minutes. Run on PRs targeting main and on main itself.

Layer 3 — E2E tests: real browser, deployed environment, real APIs. Target: under 15 minutes. Run on merge to main, before promoting to production.

Most teams run all three layers on every push. That's the behaviour you want for Layer 1, not for all three. An E2E suite on a feature branch PR creates 15 minutes of noise for a change that might be one line. Worse, E2E tests are flaky by nature — network timeouts, race conditions, timing issues. You don't want flaky gates blocking feature branch pushes.

Fail Fast: The Gate Structure

A well-structured pipeline has explicit gates. Pass a gate: proceed. Fail a gate: stop, report, and stop wasting compute. The fail-fast structure looks like this:

.github/workflows/ci.yml (simplified structure)
# Gate 1: Fast checks — should complete in under 2 minutes jobs: fast-checks: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: { node-version: '20', cache: 'npm' } - run: npm ci --prefer-offline - run: npm run lint - run: npm run typecheck - run: npm run test:unit # Gate 2: Integration — only runs if Gate 1 passed integration: needs: [fast-checks] runs-on: ubuntu-latest services: postgres: image: postgres:16-alpine env: { POSTGRES_PASSWORD: test } steps: - uses: actions/checkout@v4 - run: npm ci --prefer-offline - run: npm run test:integration # Gate 3: Build artifact — only runs if Gate 2 passed build: needs: [integration] runs-on: ubuntu-latest steps: - run: npm run build - uses: actions/upload-artifact@v4 with: { name: dist-${{ github.sha }}, path: dist/ }

The needs key is the gate. Gate 2 will not run if Gate 1 fails. Gate 3 will not run if Gate 2 fails. This means a lint error surfaces in 90 seconds, not 45 minutes.

Artifact Promotion, Not Rebuilding

This is the single most underused pattern. Most pipelines build the application separately for staging and production. Same source commit. Two builds. Two slightly different binaries. This is wrong.

What you actually want: build once, promote the same artifact through environments. The artifact is a Docker image tagged with the git SHA, or a zip file, or an S3 object. The same bytes that ran in staging are the bytes that go to production. No rebuild means no chance that a different dependency version, environment variable, or build toolchain version sneaks in.

The rule: one commit SHA → one build artifact. The artifact is immutable. What changes between environments is configuration, not code. If you rebuild for each environment, you're not doing continuous delivery — you're doing continuous building.
Artifact promotion with Docker + ECR
# Build job: runs once, tags with git SHA build: steps: - run: | docker build -t $ECR_REPO:${{ github.sha }} . docker push $ECR_REPO:${{ github.sha }} # Deploy-staging: downloads the same image, deploys with staging config deploy-staging: needs: [build] environment: staging steps: - run: | aws ecs update-service \ --cluster staging \ --service api \ --force-new-deployment \ --task-definition $ECR_REPO:${{ github.sha }} # Deploy-prod: same image, different environment variables deploy-prod: needs: [deploy-staging, e2e-staging] environment: production steps: - run: | aws ecs update-service \ --cluster production \ --service api \ --force-new-deployment \ --task-definition $ECR_REPO:${{ github.sha }}

Caching: The Biggest Easy Win

A cold npm ci on a node_modules directory with 800 packages takes 90–120 seconds. A cached restore takes 4 seconds. Over 100 pipeline runs a day, that's 24 minutes of wall-clock time saved per developer, per day.

The cache key strategy matters as much as caching itself. Cache on package-lock.json hash, not package.json. A lockfile change means real dependency changes and you want a fresh install. A package.json change might just be a description update — you don't need to bust the cache.

Correct cache key strategy
# Good: cache key on lockfile hash - uses: actions/cache@v4 with: path: ~/.npm key: npm-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }} restore-keys: | npm-${{ runner.os }}- # Also cache build outputs when inputs are deterministic - uses: actions/cache@v4 with: path: .next/cache key: nextjs-${{ runner.os }}-${{ hashFiles('**/*.ts','**/*.tsx','**/package-lock.json') }} restore-keys: | nextjs-${{ runner.os }}-

TypeScript compilation output is also cacheable. If none of your .ts files changed, tsc doesn't need to run. The incremental compiler option in tsconfig.json writes a .tsbuildinfo file — cache that file and the cache key covers all TypeScript source. A 45-second typecheck becomes a 3-second cache restore on unchanged code.

Rollback: Design It Before You Need It

Every pipeline needs a rollback path that takes under five minutes to execute. If your rollback takes 45 minutes, it's not a rollback — it's a second deployment. During an incident at 2am, the pressure to just push a fix forward is immense. That pressure exists because rollback wasn't designed in advance.

The artifact promotion pattern makes rollback almost free. You already have the previous SHA's image in ECR. Rollback is just pointing the ECS task definition back at the previous image tag. No rebuild, no waiting for tests. The same pipeline that promoted that image already validated it.

Database migrations break simple rollbacks. If the current deploy ran a migration that dropped a column, rolling back the application code doesn't bring the column back. This is why migrations must be backward-compatible. Add the column first. Deploy. Use it. Drop the old column in a separate deploy days later. Never drop in the same deploy that adds.

Blue-green maintains two identical production environments. Blue is live. Green gets the new deployment. When green is healthy, you flip the load balancer. Rollback is switching the load balancer back to blue — takes 30 seconds.

The cost: you need double the production capacity during deploys. For an ECS service with 4 tasks, you're running 8 tasks during the cutover window. On large instance types this matters. For Lambda or Fargate Spot, the cost is negligible.

# ECS blue-green with CodeDeploy
aws deploy create-deployment \
  --application-name my-app \
  --deployment-group-name prod \
  --revision imageFile=imageDetail.json

# The deployment group is configured with:
# - deployment type: BLUE_GREEN
# - termination wait time: 5 minutes (keep blue alive for quick rollback)
# - traffic routing: AllAtOnce or Canary10Percent5Minutes

The terminationWaitTimeInMinutes setting is critical. It keeps the old (blue) environment running after the switch, so rollback is instant for that window. Set it to 5–10 minutes minimum. After that window, the blue tasks are terminated and you're past easy rollback territory.

Send 5% of traffic to the new version. Watch error rates, latency, and business metrics for 10–15 minutes. If metrics are clean, increment to 25%, then 100%. If metrics degrade, roll back automatically.

This requires feature parity between the old and new version for the canary window. If you're changing the API contract, you can't run both versions simultaneously — that's a pre-condition for using canary deploys.

# AWS Lambda weighted alias
aws lambda update-alias \
  --function-name my-function \
  --name LIVE \
  --routing-config AdditionalVersionWeights={"2"=0.05}

# 5% of traffic goes to version 2, 95% stays on version 1
# CloudWatch alarm triggers rollback automatically:
# aws lambda update-alias --routing-config {} (back to 100% old)

CloudWatch Alarms are the automation layer. Define the error rate threshold before the deploy. If 5xx error rate > 1% during the canary window, the alarm fires and CodeDeploy executes a rollback automatically. No human needed at 2am.

Never bake secrets into Docker images. Never pass them as build args. The image layer history stores build args in plaintext. If the image is ever pushed to a shared registry, those secrets are exposed.

The correct pattern: inject secrets at runtime, not build time. Application reads from AWS Secrets Manager or Parameter Store on startup. The pipeline only needs the AWS credentials to deploy — it never touches the application secrets.

# Bad: secret in build arg (ends up in layer history)
docker build --build-arg DATABASE_URL=$DATABASE_URL .

# Good: ECS task definition references Secrets Manager
{
  "secrets": [
    {
      "name": "DATABASE_URL",
      "valueFrom": "arn:aws:secretsmanager:us-east-1:123:secret:prod/db-url"
    }
  ]
}

For GitHub Actions specifically, use OIDC federation with AWS. The pipeline assumes an IAM role directly, no long-lived credentials needed. The role is scoped to exactly what the pipeline needs — push to ECR, update an ECS service. Nothing more.

# OIDC-based role assumption (no ACCESS_KEY stored in GitHub)
- uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::123456789:role/github-ci-role
    aws-region: us-east-1

A flaky test that fails 10% of the time sounds minor. At 50 pipeline runs per day, that's 5 pipeline failures per day that aren't real failures. Developers learn to re-run the pipeline. The pipeline becomes a speed bump, not a quality gate. Eventually, people stop trusting the pipeline entirely.

Flakiness comes from three sources: timing (async operations with fixed waits), shared state (tests that depend on execution order), and external dependencies (tests that hit real APIs). The fix for each:

  • Timing: replace setTimeout(fn, 500) with polling: await waitFor(() => expect(el).toBeVisible(), { timeout: 5000 })
  • Shared state: each test creates and tears down its own data. No shared fixtures, no global state mutation.
  • External dependencies: mock them. If your integration test hits a real Stripe API, it's an E2E test masquerading as an integration test.

Track flakiness as a metric. GitHub Actions doesn't expose this natively, but you can query the API: gh run list --workflow=ci.yml --json conclusion,createdAt. If a test suite's failure rate exceeds 2% on unchanged code, quarantine the offending tests and fix them before re-enabling.

Pipeline Observability

Your pipeline is production infrastructure. Treat it like one. Measure pipeline duration, failure rate per stage, flakiness rate, and cache hit rate. Graph these over time. A pipeline that was taking 8 minutes three months ago and now takes 22 minutes has a problem — you just haven't noticed because there's no dashboard.

GitHub Actions exposes timing data via the REST API. A simple script that runs nightly and posts to a Datadog custom metric tells you everything: which stage is growing, when the growth started, and what commit correlated with it. This is a two-hour investment that pays back in hours of debugging time saved.

Correlate pipeline duration spikes with dependency additions. Nine times out of ten, a pipeline that started taking 8 minutes longer added a new npm package that has a large install-time compilation step (node-gyp, sharp, canvas). The fix is usually finding a pre-built binary or switching to a version that ships one.

Putting It Together

A pipeline that works has five properties: it's fast (under 5 minutes to pre-merge feedback), it's honest (a failure means something actually broke), it's safe (the artifact you test is the artifact you deploy), it's recoverable (rollback takes minutes), and it's visible (you can see its health trending over time).

None of these require exotic tooling. GitHub Actions, a caching strategy, a gate structure, OIDC auth, and a Dockerised artifact. The structure matters more than the platform. A well-structured pipeline on GitHub Actions beats a poorly structured pipeline on any enterprise CI tool.

Fix the structure first. Measure the metrics. Then optimise the slowest gate. Repeat.
