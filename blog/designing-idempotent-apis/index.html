Designing Idempotent APIs

By Pardeep Dhingra

That's a double charge. The customer gets billed twice. Your support queue fills up. Your Stripe dispute rate ticks upward. All because the API treated two identical requests as two distinct operations.

I've shipped this bug. In 2019, a payment endpoint I owned double-charged 340 customers over a weekend because our mobile client retried on timeout and the API had no idempotency protection. It took us three days to identify every affected transaction, issue refunds, and send apology emails. Total cost: ~$14,000 in refunds, a 0.3% dispute rate spike, and a lot of trust burned.

This post is the complete playbook for making APIs safe to retry.

What Idempotency Actually Means

An operation is idempotent if performing it once produces the same result as performing it N times. DELETE /users/42 is naturally idempotent: deleting the same user twice leaves you with the same state (user gone). POST /payments is not: each call creates a new charge.

HTTP gives you some idempotency for free. GET, PUT, DELETE, and HEAD are idempotent by spec. POST and PATCH are not. But "by spec" means nothing if your implementation violates it. I've seen PUT endpoints that append to a list instead of replacing it. I've seen DELETE endpoints that decrement a counter. The HTTP method is a promise, not a guarantee.

The real definition: f(x) = f(f(x)). Same input, same side effects, same response. Not "same status code" — same observable outcome in your system.

The HTTP Method Cheat Sheet

Idempotent by spec. No side effects. Same resource, same representation. Safe to retry infinitely.

Watch out for: GET endpoints that trigger analytics events or write audit logs as a side effect. If GET /report increments a "views" counter, that's technically not idempotent. Decide if you care.
Idempotent by spec. Replaces the entire resource. PUT /users/42 { name: "Pardeep" } should produce the same state whether called once or ten times.

Watch out for: PUT handlers that merge instead of replace. If your PUT does Object.assign(existing, body), it's behaving like PATCH and you lose the idempotency contract. Replace the full resource or don't call it PUT.
Idempotent by spec. First call deletes the resource. Second call finds nothing to delete — same end state.

Watch out for: Returning 404 on the second call. Technically correct, but it confuses retry logic. Consider returning 200/204 with a "already_deleted": true flag instead. Also: soft-delete toggles that re-delete (un-soft-delete) on a second call.
NOT idempotent by spec. Creates a new resource each time. This is where you need idempotency keys.

The fix: Accept an Idempotency-Key header. Store the key + response on first execution. Return the stored response on retries. More on this below.
Conditionally idempotent. Depends entirely on the operation. PATCH { "name": "Pardeep" } is idempotent. PATCH { "balance": { "$increment": 10 } } is not.

The fix: If your PATCH performs relative operations (increment, append, push), treat it like POST and require an idempotency key.

Here's the implementation. This is close to what we run in production:

idempotency-middleware.ts
import { DynamoDB } from '@aws-sdk/client-dynamodb'; const IDEMPOTENCY_TABLE = 'idempotency-keys'; const TTL_SECONDS = 86400; // 24 hours export async function idempotencyMiddleware(req, res, next) { const key = req.headers['idempotency-key']; if (!key) return next(); // Step 1: Try to claim the key with a conditional write try { await dynamo.putItem({ TableName: IDEMPOTENCY_TABLE, Item: { pk: { S: key }, status: { S: 'processing' }, ttl: { N: String(Math.floor(Date.now() / 1000) + TTL_SECONDS) } }, ConditionExpression: 'attribute_not_exists(pk)' }); } catch (err) { if (err.name === 'ConditionalCheckFailedException') { // Key exists — return cached response const existing = await getIdempotencyRecord(key); if (existing.status === 'processing') { return res.status(409).json({ error: 'Request in progress' }); } return res.status(existing.statusCode).json(existing.body); } throw err; } // Step 2: Execute the actual handler const originalJson = res.json.bind(res); res.json = async (body) => { await updateIdempotencyRecord(key, res.statusCode, body); return originalJson(body); }; next(); }

The critical line is ConditionExpression: 'attribute_not_exists(pk)'. This is an atomic compare-and-set. Two concurrent requests with the same key will race to claim it, and exactly one will win. The loser gets the cached response or a 409 "in progress" status.

Why DynamoDB? The conditional write is atomic and strongly consistent in DynamoDB. If you use Postgres, use INSERT ... ON CONFLICT DO NOTHING with a RETURNING clause. Redis works too with SET NX. The key property is: the store operation must be atomic.

The Three Storage Backends

Your idempotency store needs three properties: atomicity, TTL support, and low latency. Here's how the common options compare:

DynamoDB — Best for serverless

▼

Atomic write: ConditionExpression on putItem. Single-item transactions are strongly consistent.

TTL: Built-in. Set a ttl attribute and DynamoDB garbage-collects expired items automatically (within ~48h).

Latency: Single-digit milliseconds for single-item operations.

Cost: $1.25 per million writes (on-demand). At 100k idempotent requests/day, that's ~$3.75/month.

Downside: Eventually consistent reads by default. Use ConsistentRead: true when fetching cached responses, or you might return stale "processing" status.

PostgreSQL — Best if you already run it

▼

Atomic write: INSERT INTO idempotency_keys (key, status) VALUES ($1, 'processing') ON CONFLICT (key) DO NOTHING RETURNING *. If RETURNING gives you a row, you claimed it. If not, someone else did.

TTL: No built-in TTL. Run a cron job: DELETE FROM idempotency_keys WHERE created_at < NOW() - INTERVAL '24 hours'. Or use pg_cron.

Latency: Sub-millisecond on the same machine. 1-5ms over the network.

Cost: Free if you already have a Postgres instance. But you're adding write load to your primary database.

Downside: Adds load to your transactional database. Under heavy write contention, the idempotency table can become a bottleneck. Consider a separate read replica or a dedicated instance.

Redis — Best for raw speed

▼

Atomic write: SET idempotency:{key} "processing" NX EX 86400. NX means "only set if not exists." Returns nil if key already claimed.

TTL: Built-in with EX (seconds) or PX (milliseconds).

Latency: Sub-millisecond. Fastest option by far.

Cost: ElastiCache starts at ~$12/month for a cache.t3.micro. Upstash offers pay-per-request at $0.20 per 100k commands.

Downside: Data loss risk. If Redis restarts without persistence (AOF/RDB), all in-flight idempotency keys disappear. Use Redis Cluster with AOF appendfsync everysec for durability, or accept the small window of risk.

The Danger Zone: Concurrent Duplicate Requests

Here's the scenario that breaks naive implementations. Two identical requests arrive at the same millisecond. If your idempotency check is read-then-write (instead of compare-and-set), both reads see "no existing key," both proceed to execute, and you get a double charge.

Broken: Read-then-write
// RACE CONDITION const exists = await db.get(key); if (!exists) { await processPayment(); // Both execute! await db.set(key, result); }
Safe: Compare-and-set
// ATOMIC const claimed = await db.set( key, 'processing', { NX: true } // Only one wins ); if (claimed) { await processPayment(); }

The difference: a single atomic operation that claims the key and checks existence in one step. No gap between "check" and "claim" for another request to slip through.

Edge Cases That Will Bite You

The basic pattern is straightforward. The edge cases are where teams get burned. I've hit each of these in production.

1. Key reuse across different payloads

▼

Client sends Idempotency-Key: abc with { amount: 50 }, then reuses the same key with { amount: 100 }. Should you return the cached $50 response? Execute the $100 request?

The answer: Return a 422 error. Hash the request body and store it alongside the key. On retry, compare the hash. If it doesn't match, the client is misusing the key. Stripe does exactly this and returns "idempotency_key_in_use".

2. Handler crashes mid-execution

▼

The key is claimed (status: "processing"), but the handler throws before storing the response. Now the key is stuck. Every retry returns 409 "in progress" forever.

The fix: Add a locked_at timestamp. If a key has been "processing" for more than 60 seconds, consider it abandoned. Allow the next request to re-claim it. This is a lease pattern — the lock expires if the holder dies.

lease-check.ts
const LEASE_TIMEOUT = 60_000; // 60 seconds if ( existing.status === 'processing' && Date.now() - existing.lockedAt > LEASE_TIMEOUT ) { // Lease expired, re-claim the key await reclaimKey(key); }

3. TTL is too short

▼

You set a 1-hour TTL. Client retries after 2 hours (mobile app that went to background). The key expired. The request executes again. Double charge.

The fix: 24-hour minimum TTL. For financial operations, consider 7 days. Match your TTL to your longest realistic retry window. Stripe uses 24 hours. For webhook retries that can span days, store the idempotency record permanently in your domain table instead.

4. Natural vs. synthetic idempotency keys

▼

UUIDs work, but they push the deduplication responsibility to the client. If the client generates a new UUID per retry, idempotency is defeated.

Better approach: Use natural keys when possible. For a payment, the key could be user:{userId}:order:{orderId}. The same user paying for the same order always produces the same key, regardless of retries. This makes idempotency automatic — no client cooperation needed.

How Stripe Does It

Stripe's idempotency implementation is the gold standard. Here's what they do that most teams skip:

  • Body fingerprinting: They hash the request body and reject retries with different bodies using the same key.
  • In-progress locking: Concurrent duplicates receive a 409 while the first request is executing.
  • Stored responses: The full HTTP response (status code + body) is cached, not just a boolean "done" flag.
  • 24-hour TTL: Keys expire after 24 hours. Long enough for any reasonable retry window, short enough to not bloat storage.
  • Client-generated keys: The client sends Idempotency-Key as a header. Server never generates keys — that would defeat the purpose.
Copy this exactly. Unless you have a specific reason to deviate, Stripe's model is battle-tested across billions of API calls. Don't get creative with your idempotency implementation.

Quick Knowledge Check

A client sends the same idempotency key with a different request body. What should the server do?
Returning a 422 (or 400) is the correct approach. The client is either misusing the key or has a bug. Silently executing would break idempotency. Silently returning the old response would give the client wrong data for their actual request. The error surfaces the problem immediately. Stripe returns "idempotency_key_in_use" in this case.
Which storage operation is safe for concurrent idempotency checks?
INSERT ... ON CONFLICT DO NOTHING is a single atomic database operation. SELECT-then-INSERT has a race window between the two statements, even inside a transaction (unless you use SERIALIZABLE isolation, which has its own costs). In-memory caches don't work across multiple server instances. Application-level mutexes don't work across processes or machines.

The Implementation Checklist

Here's what to do Monday morning. This is the minimal viable idempotency setup for any POST endpoint that creates resources or triggers side effects:

  • Accept Idempotency-Key header on all POST/PATCH endpoints that have side effects.
  • Use atomic compare-and-set to claim keys. No read-then-write.
  • Store the full response (status code + body), not just a flag.
  • Hash the request body and reject mismatched retries with 422.
  • Set a 24-hour TTL minimum. 7 days for financial operations.
  • Add a lease timeout (60s) for stuck "processing" keys.
  • Return 409 for concurrent in-flight duplicates.
  • Log every cache hit with the original request ID for debugging.
  • Make the key optional on non-critical endpoints. Required on payments, transfers, anything involving money.
For your client SDK: Generate the idempotency key on the first attempt and reuse it for all retries. Store it alongside the request in your retry queue. If you're using Axios, add a request interceptor that attaches a key from a Map keyed by request URL + body hash.

When NOT to Use Idempotency Keys

Idempotency keys add latency (one extra database round-trip) and storage cost. Don't use them where you don't need them:

  • Read-only endpoints. GET is already idempotent.
  • Full-replacement PUTs. If your PUT replaces the entire resource, it's naturally idempotent.
  • Deletes with no side effects. Deleting an already-deleted resource is a no-op.
  • Internal service-to-service calls with message queues. If you're using SQS with deduplication IDs, the queue handles idempotency for you.

Use idempotency keys on: payment creation, account creation, order submission, email/notification triggers, any operation where a duplicate would cause real-world harm.

Measuring Success

After implementing idempotency, track three metrics:

  • Cache hit rate — percentage of requests that returned a cached response. Baseline: 0.1-2% for a well-behaved system. If it's higher, your clients are retrying too aggressively.
  • 409 rate — concurrent duplicates. Should be near zero. If it spikes, you have a client bug (rapid-fire requests) or a webhook delivery issue.
  • Duplicate side-effect rate — the metric you actually care about. Count double charges, double emails, double account creations. This should be zero after deployment.

We went from 0.3% duplicate charge rate to zero within a week of deploying idempotency middleware. The 409 rate settled at 0.02%, all from legitimate concurrent retries during network partitions. The extra DynamoDB cost was $4.50/month.

The bottom line: Idempotency is not optional for any API that handles money, sends notifications, or creates user-visible state. The implementation takes a day. The alternative is explaining to 340 customers why they got charged twice.
