WebSockets at Scale

By Pardeep Dhingra

Last Tuesday at 2:14 AM, our WebSocket gateway dropped 23,000 connections in 90 seconds. The cause wasn't a bug. It was a routine deployment — a rolling restart of four EC2 instances behind a Network Load Balancer. Every connection on the restarting instance died instantly. No graceful drain. No reconnect backoff. Just 23,000 clients hammering the remaining three nodes simultaneously, which promptly buckled under the thundering herd.

The fix took six lines of code. Understanding why those six lines mattered took three years of running WebSocket infrastructure in production. This post is the distilled version.

HTTP vs WebSocket: The Connection Model

HTTP is stateless. Every request is independent — load balancers can route each one to any backend. WebSockets are the opposite. Once the handshake completes, the client is bound to a specific server process for the life of the connection. That single difference changes everything about how you deploy, scale, and debug.

HTTP Request Model

Stateless. Each request is independent.

Load balancer picks any backend per request.

Server crash affects only in-flight requests.

Scaling: add nodes, update LB. Done.

WebSocket Connection Model

Stateful. Connection persists for minutes to hours.

Client is pinned to one backend after handshake.

Server crash kills all connections on that node.

Scaling: drain connections, rebalance, manage state.

This statefulness is where every WebSocket scaling problem originates. Your infra needs to account for three things HTTP doesn't care about: connection affinity, connection lifecycle, and cross-node messaging.

Clients connect via wss://. The critical client-side decisions: exponential backoff on reconnect (start at 1s, cap at 30s, add jitter), sequence numbering for gap detection, and a local message queue that buffers during disconnection. Without these, every network hiccup becomes a data loss event.
Network Load Balancer operates at L4 (TCP). It doesn't inspect HTTP headers, so it can't do path-based routing — but it handles millions of concurrent connections with single-digit microsecond latency. Use NLB for raw WebSocket traffic. Use ALB if you need path-based routing (/ws/chat vs /ws/notifications) — but know that ALB has a 4,000 new-connections-per-second limit per target. For most WebSocket workloads, NLB is the right default.
WebSocket Nodes hold the actual connections in memory. Each Node.js process can handle ~65K connections before memory becomes the bottleneck (not CPU). The key insight: these nodes are stateful. You can't just kill them during deploys. You need a drain period where the node stops accepting new connections, sends a "please reconnect" frame to existing clients, and waits for them to migrate. 30 seconds is a good drain timeout for most workloads.
Redis Pub/Sub is the fan-out layer. When user A on Node 1 sends a message to user B on Node 3, the message goes: Node 1 → Redis channel → Node 3 → user B's socket. Redis Pub/Sub has zero persistence — if Node 3 is temporarily disconnected from Redis, those messages are gone. For durability, use Redis Streams instead of Pub/Sub, or layer a message queue (SQS, Kafka) underneath.
Connection Store maps userId → {nodeId, socketId, connectedAt}. This is how you know which node holds a user's connection. Redis with a TTL of 2x your heartbeat interval works well. When a node dies, its entries expire automatically. DynamoDB works too if you need persistence, but adds 5-10ms latency per lookup — fine for routing, too slow for presence detection.

Connection Lifecycle: The Six States

Every WebSocket connection moves through six distinct states. Most bugs happen during transitions between them — especially the ones your code doesn't explicitly handle.

connection-states.ts
enum ConnectionState { CONNECTING = 'connecting', // Handshake in progress AUTHENTICATING = 'authenticating', // WS open, awaiting auth token ACTIVE = 'active', // Fully connected, sending/receiving DRAINING = 'draining', // Server shutting down, please reconnect RECONNECTING = 'reconnecting', // Client-side backoff loop DEAD = 'dead', // Max retries exceeded, give up } // The state most people miss: AUTHENTICATING // An open WebSocket without auth is a DoS vector. // Enforce a 5-second auth timeout after connection. const AUTH_TIMEOUT_MS = 5000; ws.on('connection', (socket) => { const timer = setTimeout(() => { socket.close(4001, 'Auth timeout'); }, AUTH_TIMEOUT_MS); socket.once('message', (msg) => { clearTimeout(timer); const token = parseAuthMessage(msg); if (!verifyToken(token)) { socket.close(4003, 'Invalid token'); return; } // Transition: AUTHENTICATING -> ACTIVE promoteToActive(socket, token.userId); }); });

The DRAINING state deserves special attention. Here's the six-line fix I mentioned at the start:

graceful-drain.ts
// SIGTERM handler — triggered by rolling deploys process.on('SIGTERM', () => { server.close(); // Stop accepting new connections for (const ws of activeConnections) { ws.send(JSON.stringify({ type: 'drain', reconnectAfter: 2000 })); ws.close(4000, 'Server draining'); } setTimeout(() => process.exit(0), 30000); // Force exit after 30s });

The client receives the drain message, waits 2 seconds (plus jitter), then reconnects. The staggered reconnect prevents the thundering herd. Without this, every client reconnects at the exact same millisecond.

Heartbeats and Timeouts

TCP connections can go half-open — one side thinks it's connected, the other has moved on. The internet is full of NAT gateways, mobile carriers, and corporate proxies that silently drop idle connections after 30-60 seconds. Heartbeats are how you detect this.

The recommended values depend on your use case:

Ping interval: 25 seconds. Pong timeout: 5 seconds.

Chat apps tolerate a few seconds of staleness. 25s keeps connections alive through most NAT timeouts (which typically fire at 30-60s) without burning bandwidth. At 10K connections, this is ~400 ping/pong pairs per second — trivial for a single Node.js process.

Reconnect strategy: Exponential backoff starting at 1s, capped at 30s, with ±20% jitter.

Ping interval: 45 seconds. Pong timeout: 10 seconds.

Notification connections are long-lived and low-frequency. Users won't notice a 10-second detection delay. The longer interval saves battery on mobile — each ping wakes the radio, costing ~5mA per ping on LTE. At 45s intervals, that's 80 pings per hour vs 144 at 25s — a 44% reduction in radio wake-ups.

Reconnect strategy: Exponential backoff starting at 2s, capped at 60s. Add visibility check — don't reconnect if the tab is hidden.

Ping interval: 5 seconds. Pong timeout: 2 seconds.

In trading and gaming, a stale connection means stale data, which means wrong decisions. You need to detect disconnection within 7 seconds total. The bandwidth cost is higher (~2,000 ping/pong pairs per second at 10K connections), but the data integrity requirement justifies it.

Reconnect strategy: Immediate first retry, then 500ms, 1s, 2s, 4s cap. No jitter needed — these clients are usually on dedicated infrastructure.

Fan-Out: Getting Messages to the Right Socket

Here's the problem: User A is on Node 1. User B is on Node 3. A sends a message to B. How does it get there?

Three approaches, each with distinct tradeoffs:

1. Redis Pub/Sub (Simple, No Durability)

▼

Every WS node subscribes to a Redis channel (one per user, or one per "room"). When Node 1 needs to reach User B, it publishes to user:B. Node 3 receives it and forwards to B's socket.

Pros: Dead simple. Single Redis instance handles 500K messages/sec. Sub-millisecond latency.

Cons: Fire-and-forget. If Node 3 is temporarily disconnected from Redis, the message is lost. No replay. No ordering guarantees under failure.

Use when: Messages are ephemeral (typing indicators, presence updates, cursor positions) or your app has a separate persistence layer that clients can query on reconnect.

redis-fanout.ts
// Publisher side (Node 1) await redis.publish( `user:${targetUserId}`, JSON.stringify({ type: 'message', payload, seq: nextSeq() }) ); // Subscriber side (Node 3, on startup) redis.psubscribe('user:*', (channel, message) => { const userId = channel.split(':')[1]; const socket = connections.get(userId); if (socket) socket.send(message); });

2. Redis Streams (Durable, Ordered)

▼

Same idea as Pub/Sub, but messages are persisted in a Redis Stream with auto-generated IDs. Each WS node runs a consumer group. If a node goes down, messages accumulate in the stream and are delivered when the node recovers (or another node claims the pending entries).

Pros: Durable. Ordered. Consumer groups handle exactly-once delivery semantics. Backpressure via XREADGROUP BLOCK.

Cons: More complex. You need to manage stream trimming (MAXLEN ~10000) or they'll eat your Redis memory. Consumer group ACKs add latency (~1-2ms overhead vs Pub/Sub).

Use when: Message ordering matters and you can't tolerate gaps. Chat applications. Collaborative editing. Anything where "did the message arrive?" is a product requirement.

3. Direct Node-to-Node (Lowest Latency)

▼

Each WS node maintains a gRPC or HTTP/2 connection to every other WS node. When Node 1 needs to reach a user on Node 3, it looks up the connection store, finds the target node, and sends directly. No Redis in the hot path.

Pros: Lowest possible latency. No external dependency in the message path. Good for small clusters (3-8 nodes).

Cons: O(n²) connections between nodes. At 20 nodes, that's 380 inter-node connections. Service discovery becomes critical — a stale routing table means dropped messages. Much harder to operate than Redis-based approaches.

Use when: You have a small, stable cluster and sub-millisecond fan-out latency is a hard requirement. Trading platforms. Real-time gaming with tight tick rates.

The Thundering Herd Problem

This is the most common WebSocket scaling failure. A node goes down (deploy, crash, OOM). All its clients reconnect simultaneously. The remaining nodes get hit with a connection spike that's 2-4x their normal rate. If they can't absorb it, they start rejecting connections, which causes more reconnects, which causes more load. Cascade failure in under 30 seconds.

The fix is a three-layer defense:

Layer 1: Client-side jitter. Don't reconnect at exactly baseDelay * 2^attempt. Add random jitter: delay * (0.8 + Math.random() * 0.4). This spreads reconnections over a 40% window.
Layer 2: Server-side admission control. Track new connections per second. When the rate exceeds a threshold (e.g., 500/sec), return HTTP 503 during the WebSocket handshake. The client's backoff logic handles the rest.
Layer 3: Graceful drain. Before killing a node, send the drain frame with staggered reconnectAfter values. If you have 10K connections, spread the reconnects over 10 seconds: reconnectAfter: Math.random() * 10000.

AWS API Gateway WebSocket: When to Use It

AWS offers a managed WebSocket API via API Gateway. It handles connection management, routing, and auto-scaling. Sounds perfect — until you look at the constraints.

Use API Gateway WS When

< 10K concurrent connections

Messages are infrequent (< 1/sec per client)

You want zero server management

Backend is Lambda-based already

Use Self-Managed When

> 10K concurrent connections

High-frequency messages (gaming, trading)

You need custom protocols (binary, protobuf)

Cost: APIGW charges $1/million messages + $0.25/million connection-minutes

At 50K connections sending 1 message per second, API Gateway costs roughly $4,320/month just for message routing. Four c6g.large EC2 instances running the same workload cost $196/month. The managed service makes sense at small scale — but the economics invert fast.

Memory: The Real Bottleneck

CPU is rarely the bottleneck for WebSocket servers. Memory is. Each WebSocket connection consumes memory for the socket buffer (kernel-space), the parsed frame buffer (user-space), and any application state you attach (user ID, room memberships, pending messages).

Baseline memory per connection in Node.js with the ws library:

memory-breakdown.txt
// Per-connection memory (Node.js + ws library) Kernel TCP buffer: ~87 KB (send + receive, tunable via sysctl) ws frame parser: ~4 KB V8 object overhead: ~2 KB App state (typical): ~1-8 KB (userId, rooms[], metadata) // --- Total: ~34 KB per connection (with optimized buffers) ~94 KB per connection (default Linux settings) // At 65K connections: Optimized: 65000 × 34 KB = ~2.1 GB Default: 65000 × 94 KB = ~5.9 GB // Key sysctl tuning (add to /etc/sysctl.conf): net.core.rmem_default = 8192 net.core.wmem_default = 8192 net.core.rmem_max = 16384 net.core.wmem_max = 16384 net.ipv4.tcp_rmem = 4096 8192 16384 net.ipv4.tcp_wmem = 4096 8192 16384

That sysctl tuning alone takes you from 5.9 GB to 2.1 GB for the same 65K connections. It's the single highest-impact optimization you can make.

Production Checklist

This is the checklist I run through before deploying any WebSocket service. Each item is a lesson learned from a production incident.

Your WebSocket server handles 40K connections. During a rolling deploy, you restart 1 of 4 nodes. How many connections hit the remaining 3 nodes simultaneously?
Without graceful draining, all 10,000 connections on the dying node close simultaneously. Every client's onclose fires at the same instant, and without jitter, they all attempt reconnection within the same 1-2 second window. This is the thundering herd. The fix: send a drain message with staggered reconnectAfter values before shutting down.
You're using Redis Pub/Sub for cross-node messaging. Node 3 loses its Redis connection for 8 seconds, then reconnects. What happens to messages published during those 8 seconds?
Redis Pub/Sub has zero message persistence. If a subscriber is disconnected when a message is published, that message is lost forever. This is by design — Pub/Sub is optimized for speed, not durability. If you need guaranteed delivery, use Redis Streams with consumer groups, or layer a persistent queue (SQS, Kafka) underneath your fan-out layer.

Monday Morning Checklist

Here's what to do with this information, in priority order:

1. Add graceful drain to your SIGTERM handler. If you deploy WebSocket servers without draining, you're causing a thundering herd on every deploy. This is the single most impactful fix — six lines of code, zero architectural changes.

2. Tune your heartbeat interval. If you're using the default ws library with no ping/pong, you have zombie connections consuming memory. Set ping interval to 25s, pong timeout to 5s. Adjust per the use-case table above.

3. Tune kernel TCP buffers. Run sysctl net.core.rmem_default on your WS servers. If it's 212992 (208KB — the Linux default), you're using 3x more memory per connection than necessary.

4. Add client-side reconnect jitter. If your reconnect logic is delay * 2^attempt without randomization, add it: delay * 2^attempt * (0.8 + Math.random() * 0.4). This prevents synchronized reconnection storms.

5. Instrument connection lifecycle. Emit metrics for connections opened, closed, errored, and time-in-state. You can't fix what you can't see. A connection that sits in AUTHENTICATING for 30 seconds is a leak. A spike in RECONNECTING events is an early warning of node failure.

6. Load test with connection churn, not just volume. Static 10K connections is a different beast than 10K connections with 500 disconnects/reconnects per second. Your load tests need to simulate the reconnection pattern, not just the steady state.

The key insight: WebSocket scaling isn't about handling more connections. It's about handling connection transitions — the connect, disconnect, reconnect, drain, and rebalance events that HTTP never has to think about. Get the lifecycle right and 65K connections per node is comfortable. Get it wrong and 5K connections will take you down.
