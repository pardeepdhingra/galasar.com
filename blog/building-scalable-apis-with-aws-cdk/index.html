Building Scalable APIs with AWS CDK and Lambda

Mar 25, 2026 Architecture AWS CDK

Over the past few years, I've built dozens of serverless APIs on AWS. Along the way, I've developed a set of patterns and conventions that make CDK-based APIs more maintainable, testable, and production-ready. This post shares the approach I use daily.

The Problem with "Quick Start" Serverless

Most CDK tutorials show you a single Lambda behind an API Gateway and call it a day. That's fine for a demo, but production APIs need structure. You need authorization middleware, request validation, structured error handling, observability, and a clean separation between your infrastructure code and business logic.

Without these patterns, serverless projects tend to become a tangled mess of Lambda functions with duplicated boilerplate and inconsistent error responses.

Architecture Overview

Here's the high-level structure I use for every new API service: 

service/
  ├── lib/
  │   ├── constructs/        # Reusable CDK constructs
  │   ├── stacks/            # CDK stacks
  │   └── config.ts          # Environment config
  ├── src/
  │   ├── handlers/          # Lambda entry points
  │   ├── middleware/         # Auth, validation, logging
  │   ├── services/          # Business logic
  │   ├── repositories/      # Data access layer
  │   └── types/             # Shared TypeScript types
  └── tests/
      ├── unit/
      └── integration/

The key insight is separating the CDK infrastructure (lib/) from the application code (src/). Your Lambda handlers should be thin — they parse the event, call the service layer, and return a response. All the interesting logic lives in services/.

The Middleware Pattern

Instead of repeating authorization checks, input validation, and error handling in every handler, I use a middleware wrapper that composes these concerns: 

export const withMiddleware = (handler: Handler, options: MiddlewareOptions) => {
  return async (event: APIGatewayEvent) => {
    try {
      // 1. Parse and validate request
      const request = parseRequest(event, options.schema);

      // 2. Authorize
      if (options.auth) {
        await authorize(event, options.auth);
      }

      // 3. Execute handler
      const result = await handler(request);

      // 4. Return structured response
      return formatResponse(200, result);
    } catch (error) {
      return formatError(error);
    }
  };
};

This keeps every handler clean and consistent. New endpoints take minutes to scaffold because the cross-cutting concerns are already handled.

CDK Constructs for Consistency

I create a base ApiLambda construct that standardizes how every Lambda is configured — memory, timeout, environment variables, log retention, tracing, and alarms. New endpoints inherit these defaults, and you can override per-function where needed.

The best infrastructure code is boring. It should be predictable, consistent, and easy for any team member to extend.

What I'd Do Differently

If I were starting fresh today, I'd invest earlier in contract testing between services. Integration tests catch a lot, but as your service count grows, contract tests (using something like Pact) pay for themselves quickly.

I'd also consider using Powertools for AWS Lambda from day one for structured logging, tracing, and metrics — it removes a lot of custom boilerplate.

Key Takeaways

  • Separate infrastructure code from application code — they change for different reasons
  • Use a middleware pattern to DRY up cross-cutting concerns
  • Create base CDK constructs that enforce team conventions
  • Invest in testing at every layer: unit, integration, and contract
  • Keep Lambda handlers thin — push logic into service classes

Building scalable APIs is less about the technology and more about the patterns you establish early. Get the structure right, and adding new endpoints becomes a joy rather than a chore.
